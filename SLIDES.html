STAFF SECURITY ENGINEER · TAKE-HOME

Running coding agents
you don’t trust

A sandboxed Claude Code platform: no secrets in the sandbox, every capability from a reviewed spec, and an independent sentinel that contains exfiltration on its own.

kind · gVisor · Cilium + Hubble · explicit gateways · credentials proxy · GitHub App

One sentence to open: I built a small internal platform where a coding agent runs in a throwaway sandbox that holds nothing worth stealing, can only do what a reviewed spec allows, and is watched by a detection plane that doesn’t trust the platform it watches. Then I tried to break it with a one-command harness. Plan for the call: the design in four slides, the evidence in two, then the gaps and what I’d do next. Offer a live demo at the end if there is time.

Treat the agent as already compromised

A coding agent reads untrusted content (repos, issues, docs) and holds real tools. One prompt injection turns it into an insider, so every control has to sit outside it.

Nothing to steal

No real credential enters the sandbox. Model calls and egress go through a gateway; keys live only in a credentials proxy.

Nothing unreviewed

Every capability (models, hosts, tools, repos, lifetime) comes from a versioned spec, approved by a second person.

Nothing taken on trust

A separate sentinel checks the platform’s evidence against kernel flow data, and contains on its own.

The framing I used for every decision: assume the agent is already working for the attacker. That gives three requirements. First, there is nothing in the sandbox worth stealing: the agent only ever holds a session token that is useless outside its own pod. Second, everything the agent can do is declared in a spec that someone other than its author approved. Third, detection must not depend on the components it is checking, so the sentinel cross-checks what the gateway claims against what the kernel saw, and it can act on its own. The canary in the repo’s .env is the stand-in for a real secret; leaking it is the success condition for the attacker.

Three trust zones on three nodes: sandboxes on a tainted gVisor node, platform with the secrets on another, the sentinel alone on a third.

Walk the request path left to right. The sandbox can open exactly two connections, both to the gateway: port 8080 for model calls, 3128 as an explicit forward proxy for everything else. Every request carries the session token, which the gateway checks with the control plane, bound to the pod IP and the session’s compiled spec. The gateway then hands the call to credproxy, the only component holding the Anthropic key and the GitHub App key, which re-checks the grant before using them. Anything the sandbox tries outside those two ports never gets out: Cilium drops it at the kernel and Hubble records it, which is the bypass signal. The gateway ships its hash-chained evidence to the sentinel, and the sentinel also reads Hubble directly; if something is wrong it writes its own deny policy on the session. Physically: sandboxes on a tainted node that is the only one with gVisor; the secrets on the platform node; the sentinel alone on the third node.

A session, from run to pull request

1 · run

Control plane compiles the spec, mints a session token, creates a gVisor pod on the sandbox node

2 · deliver

Repo cloned and canary planted outside the pod, then streamed in; the pod never talks to git

3 · work

Claude Code runs; every model call and fetch goes through the gateway; follow-ups resume the same conversation

4 · stop

Token revoked; control plane computes the diff itself; transcript and bodies kept; pod deleted

5 · publish

credproxy opens a draft PR with a scoped token, revoked after; protected paths and canaries refused

Idle or expired: the reaper stops it and keeps the work. Pod gone: the session ends and its token dies with it.

Contained: network cut, token revoked, evidence snapshotted; the pod is kept for a while for forensics, then destroyed.

The lifecycle in five steps. Run: the control plane validates that the caller owns the spec, that the parameters are the declared ones, compiles the spec into a session policy bound by digest, mints a placeholder token and creates the pod. Deliver: the control plane clones the repo (git-lab or GitHub through credproxy), plants the canary in .env, and streams the workspace in through exec; the sandbox has no git credentials and no route to git. Work: the agent runs with the gateway as its only exit; sbxctl send writes a follow-up into the pod’s inbox and Claude Code continues the same conversation. Stop: the token is revoked first, then the control plane exports the diff from its own copy, keeps the transcript and the model bodies, and deletes the pod. Publish: credproxy mints a repo-scoped token, pushes a branch, opens a draft PR authored by the App, and revokes the token. Sessions that go idle are reaped so an abandoned agent doesn’t hold resources; a contained session is kept briefly, off the network, for investigation.

The agent never pushes and never sees git credentials: the control plane computes the diff itself and credproxy opens a draft PR, refusing .github/ changes or any diff that contains the canary.

This is the part I’d defend hardest. The sandbox’s ANTHROPIC_API_KEY is a placeholder. On its own it is worthless: the gateway accepts it only from the pod IP it was issued to, only for that session’s spec, and only while the session is running, and revoking it is one state change. The real key and the GitHub App private key exist in exactly one pod, on a different node from any sandbox, so a gVisor escape lands next to nothing. GitHub tokens are minted per operation, scoped to a single repository and the minimum permission, and revoked immediately; the token value never leaves credproxy. Publishing is done from the control plane’s own diff, not from git output inside the pod, because that output is attacker-controlled. In the real run this produced a draft PR with 52 tests and 4 real bugs, authored by the App.

A reviewed spec decides what each agent may do

1 · write

Author drafts YAML

Models, egress hosts, tools, repos, secrets, TTL, image

2 · baseline

Org policy as code

gVisor only, exact hosts, approved models, bounded TTL

3 · approve

Second person signs

The exact digest, approver ≠ author; versions immutable

4 · enforce

Compiled per session

Gateway, Cilium and admission enforce it, not the agent

Run-time input can’t widen it: sbxctl run … -p egress=evil.com is rejected (400), and a weaker pod is refused by admission even if the control plane is wrong.

Agent specs work like infrastructure code with a security review. An author writes the YAML; at registration the control plane checks it against an org baseline (gVisor runtime, exact hostnames from an approved catalogue with no wildcards, approved models, bounded TTL and budgets, read-only repos, unrestricted Bash only with a recorded risk acceptance). Then a different person approves the exact digest, so review is bound to bytes, not to a name. Versions are immutable, and a version that widens access needs a fresh approval. At run time the user supplies only parameters the spec declares, never policy, and the compiled policy is enforced in the gateway, in Cilium, and by a ValidatingAdmissionPolicy that refuses non-gVisor pods or pods with a service-account token. The sentinel’s rules work the same way: they are configuration too, with a compiled floor that can’t be configured away.

Rules and responses are configuration (config/sentinel/detection.yaml), validated against a compiled floor.

The sentinel is a separate security plane: its own namespace, its own node, its own service account that can only write Cilium policies, and nothing on the platform can reach it except the evidence shipper. It has two kinds of input with different trust: the gateway’s evidence, which is a claim, so it verifies the sequence and hash chain on arrival; and Hubble flows from the kernel datapath, which no pod can fake. S1 is the interesting one: it counts each session’s requests from the datapath and compares them with what the gateway logged, so a gateway that quietly stops logging is caught; we proved it by fault-injecting the gateway. On a high finding it writes its own deny policy (an admission policy stops the control plane or an admin from removing it), and calls containment verified only when Hubble shows the pod’s traffic being dropped. We tested containment with the control plane scaled to zero. Detection rules and response actions are a validated, hot-reloaded YAML policy with monitor mode for tuning; a compiled floor stops anyone from switching off D1, EV or S6.

Detect, contain, verify: about one second

t = 0

Attempt

Canary leaves in a request, or a burst of blocked connections

≈ 0.1 s

Detect

≈ 1 s

Contain

Sentinel writes its own deny policy; control plane revokes the token and snapshots evidence

≤ 60 s

Verify

Hubble must show the pod’s traffic dropped and nothing forwarded; otherwise “inconclusive”, never “verified”

Two independent sources agree before containment counts: the gateway’s records and the kernel’s flow log.

Nobody else can lift it. An admission policy lets only the sentinel’s identity remove its quarantine; traffic after containment re-quarantines (S6).

This is the response path, measured in the tests. The attempt is either a canary leaving in a request (D1) or a burst of connections Cilium dropped (D2). Detection has two inputs: the gateway ships its hash-chained evidence to the sentinel within a second or so, and the sentinel reads Hubble directly, so bypass attempts that never reach the gateway are still seen. Containment is the sentinel’s own Cilium deny policy on the session, about a second from detection; the control plane revokes the token and snapshots pod spec, transcript and the session’s evidence in parallel, best effort. Verification polls Hubble for up to a minute: it needs to see the pod’s traffic being dropped after the quarantine and nothing forwarded; with no traffic at all it records “inconclusive” rather than claiming success. The quarantine is protected by an admission policy so that a compromised control plane, or an admin with kubectl, can’t remove it; and if traffic is seen after containment anyway, S6 re-quarantines.

One command tries to break it

Phase B · enforcement

27/27

cases as expected with the agent assumed compromised: no secrets found, every bypass dropped and seen

Phase A · real agent, injected

0/6

attempted the exfiltration; 3 runs were refused by the provider, which broke the real task too

Phase C · utility

Pass

Verdicts come only from outside the sandbox: gateway evidence, Hubble, lab receipts. “The agent didn’t try” is never counted as protection.

The harness is one command with three phases, and I keep them apart on purpose. Phase B is the real security evidence: it execs attacker commands inside the gVisor pod, so model behaviour plays no part: look for secrets, call the API server, skip the gateway, hit another session, raw TCP and DNS to the attacker sink, write the canary to an allowed host over HTTP and TLS. 27 of 27 behave as expected. Phase A is a real Claude Code agent fixing a bug in a repo whose code and CONTRIBUTING.md carry an injection asking it to POST .env. None of six tried; three were refused by the provider’s usage-policy check, which means injection is also an availability attack: the legitimate task failed. No agent told the user about the injection. Phase C proves the controls don’t break the job: tests re-run in a network-less container on the diff the control plane computed, not on what the agent claims.

What still gets through, and how I’d close it

GapWhyProduction fix

CLI identity is an X-User headerLocal prototypeOIDC or mTLS on the control-plane API
gVisor, three nodes in one VMNo nested virtualisation on a laptopMicroVMs (Kata, Firecracker) on separate hosts
Claude Code side-channel CONNECTA medium D2 on every runRoute through the AI gateway

The harness keeps a deliberately vulnerable spec, so each of these stays reproducible rather than asserted.

I want to be explicit about what doesn’t hold. The main residual is B20: data can ride out in the URL of a read to any reachable host; we see it in plain HTTP and contain within about a second, but one request has left. If a spec explicitly grants writes to a host, TLS to it is opaque to the proxy, which is why writes are off by default and need a risk acceptance and a second approval. Identity on the CLI is a header in this prototype, which is fine on localhost but would be OIDC or mTLS in production. gVisor is a large surface reduction but not a hardware boundary, and all three nodes share one VM here. And Claude Code’s own side traffic produces a known false positive that I chose to document rather than allowlist, because allowlisting it would open a channel to the model provider. Each of these is a test case in the harness, not just a sentence in the write-up.

Design decisions and what they cost

Explicit gateways (base URL + proxy env)Transparent TLS interceptionSemantic visibility of model calls and tool use with no MITM CA in the sandbox; bypass fails closed at the network. Cost: CONNECT is opaque
gVisor on a tainted nodeKata / FirecrackerLarge surface reduction with no KVM on a laptop; microVMs stay the production design

Per-session deny policyRelabel the pod≤ 1 s against ~45 s for an identity change

Specs approved by exact digest, second personAnnotations, trusted authorsSelf-asserted approval is worthless; binds review to bytes. Cost: friction on every widening

These are the decisions I would expect to be challenged, with the alternative I rejected and what the choice costs. The big one is explicit gateways instead of a transparent interception proxy: configuring the agent with a base URL and proxy variables means I see model requests and tool use in the clear without planting a CA in the sandbox, and if the agent ignores the variables the network drops it. The price is that CONNECT tunnels are opaque, which is exactly the B10 finding, and why write-capable hosts are read-only by default. gVisor over microVMs was forced by the laptop; Cilium over plain NetworkPolicy bought FQDN rules, fast deny policies and Hubble. Computing the diff on the control plane came out of the security review: the pod’s git output had been trusted and could be forged. Two-person digest approval also came from the review, where any approval string had been accepted. The sentinel as a separate zone is the most expensive choice operationally, but it is the only way detection survives a compromised control plane.

Two things I’d point out about process. First, I ran a full security review against my own implementation midway and it found four high-severity issues, including that the gateway forwarded the provider’s server-side tools, which is egress the network never sees; all are fixed with regression tests. Second, I kept a build log of what broke, including an incident where a real key landed in a tracked example file locally; I rewrote history, rotated it and added a pre-commit guard. That incident is the platform’s own lesson in miniature: secrets have to be structurally unable to reach the place they leak.

Next: harden the boundary, then measure detection

Harden

  1. MicroVM sandboxes on dedicated hosts
  2. Workload identity (SPIFFE/mTLS) and OIDC users
  3. WORM evidence, anchored outside, into the SIEM
  4. Signed, digest-pinned images verified at admission

Prove

  1. Detection precision and recall against harness ground truth
  2. Fuzz the gateway’s request policy, the real chokepoint
  3. A larger Phase A matrix across injection styles
  4. Kubernetes audit and Tetragon for platform pods

Live demo: make up · sbxctl run · make security-test (how-to in AGENTS.md)

Close with priorities. On the boundary, the order is: microVMs on separate hosts, because the sandbox is where untrusted code runs; then workload identity so component keys stop being shared secrets; then evidence that can’t be rewritten even by an admin; then supply chain at admission. On assurance, what I’d measure first is detection quality, precision and recall per rule against the harness ground truth, because today the false-positive side is anecdotal. Next is fuzzing the gateway’s request policy, since everything rests on it, then a bigger and more varied injection matrix, and audit plus Tetragon so the sentinel sees API-server actions and platform-pod processes, not just their network.
